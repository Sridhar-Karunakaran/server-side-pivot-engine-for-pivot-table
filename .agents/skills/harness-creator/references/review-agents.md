# Generating Framework-Aware Review Agents

A generic "review this code" agent produces generic findings: naming, comments,
"consider extracting a method". It misses the defects that actually ship, because
those are framework-specific and often invisible in a diff.

A generated reviewer differs in four concrete ways.

## 1. Structure comes from a tool, not from skimming

The original harness had the generator "read 2-3 representative source files" to
infer architecture. That produces a plausible guess. Use a tool instead:

| Stack | Tool | Output |
|---|---|---|
| .NET | `dotnet sln list` + `dotnet list reference` per project | real project dependency graph |
| .NET (deeper) | ArchUnitNET tests | executable layer rules |
| JS/TS | `depcruise --output-type json` | module graph, cycles, orphans |
| JS/TS (quick) | `madge --json src` | import graph |
| Any | `git log --format= --name-only \| sort \| uniq -c \| sort -rn` | change hotspots — where bugs actually live |

The generator writes this into `.agent/project-context.md` as a **real map with
real directory names**, and the reviewer receives it. "Put the service in the
right place" is only actionable when the reviewer knows where that is.

The `git log` hotspot query is the cheapest high-value signal available and is
almost always skipped: files changed most often are where defects concentrate, so
the reviewer weights findings there.

## 2. The defect catalog is the review checklist

Each profile names a catalog in `catalogs/`. The reviewer works that catalog, not
its own intuition. Catalog entries are paired with an analyzer rule id where one
exists, which produces the reviewer's most valuable behaviour:

> **When a rule exists but is not enabled, the finding is the missing
> configuration — not the individual instance.**

One config change prevents the class forever. Fifty review comments fix fifty
instances and prevent nothing. So the reviewer's first pass is over configuration
files, not source.

## 3. Findings must state how they are verified

Every finding carries a mandatory `Verify:` line. This is what stops the reviewer
becoming another source of confident, unverified assertions:

```
[A1] Subscription never unsubscribed
  File:   src/app/orders/order-list.component.ts:47
  Rule:   rxjs-angular/prefer-takeuntil (NOT ENABLED in eslint.config.js)
  Why:    OrderListComponent subscribes to orderService.updates$ in ngOnInit with
          no teardown. Each navigation to this route leaks the component and its
          entire template subtree; the service is providedIn:'root' so the
          subscription outlives every instance.
  Fix:    updates$.pipe(takeUntilDestroyed(this.destroyRef)).subscribe(...)
  Config: enable rxjs-angular/prefer-takeuntil as 'error' - this prevents the
          whole class, not just this instance.
  Verify: PARTIAL. The lint rule confirms the pattern is gone. Confirming the
          leak is actually fixed needs the memlab gate, which is not configured
          in this project. Recommend adding it before claiming the leak is fixed.
```

Three properties matter here. The rule id is named **and** its enabled state is
reported. The `Config:` line offers the class-level fix. And `Verify:` is honest
about being partial — the reviewer does not claim a leak is fixed on the strength
of reading a diff.

## 4. Scope is the diff, weighted by risk

The reviewer reads `git diff <baseSha>..HEAD`, not the repository. Ordering:

1. **Configuration files in the diff** — a disabled rule, a lowered threshold, a
   new suppression. Highest value, always first.
2. **Risk-gated paths** — anything matching `requiresHumanApproval`. Auth,
   migrations, public API, package manifests.
3. **Change hotspots** — files with high historical churn.
4. **Everything else** in the diff.

## Generated reviewer template

The generator writes `.agent/agents/reviewer.md` from this shape:

```markdown
# Code Reviewer — {{PROJECT_NAME}} ({{PROFILE_NAME}})

You review one task's diff. You do not review the repository.

## Inputs
- Diff:      git diff {{BASE_SHA}}..HEAD
- Spec:      .agent/tasks/{{TASK_ID}}.md  (## What and ## Plan)
- Context:   .agent/project-context.md   (architecture map, conventions, boundaries)
- Catalog:   {{CATALOG_PATH}}             (the checklist — work it systematically)
- Evidence:  .agent/evidence/{{TASK_ID}}/gate-summary.json

## Architecture (generated by tooling, not inferred)
{{ARCHITECTURE_MAP}}

## Change hotspots (high historical churn — weight findings here)
{{HOTSPOTS}}

## Procedure

1. **Read the gate evidence first.** Gates already cover what they cover. Do not
   re-litigate them, and never contradict them: if `coverage-diff` passed, do not
   claim the code is untested. Your job is the residue tools cannot check.

2. **Review configuration changes in the diff.** Report as findings, highest
   priority:
   - a lint/analyzer rule disabled, downgraded, or newly suppressed
   - a gate threshold lowered in harness.yaml
   - `eslint-disable`, `#pragma warning disable`, `[SuppressMessage]`,
     `[ExcludeFromCodeCoverage]`, `# pragma: no cover` added without a written
     justification
   - a test deleted, skipped, or its assertions weakened

3. **Work the catalog.** For each applicable entry, check the diff. Skip entries
   the diff cannot trigger, and say which sections you skipped and why.

4. **Check conventions and boundaries** from project-context.md. A boundary
   violation is always a finding regardless of code quality.

5. **Report.** Use the finding format above. Every finding needs File, Rule, Why,
   Fix, and Verify. Omit any of those and the finding is incomplete.

## Hard rules

- **Never assert what a tool should measure.** No "no memory leaks", "no
  performance regression", "this is secure", "no race condition". Report the
  *candidate* and name the gate that would verify it. If no gate exists, say
  "UNVERIFIED - no gate covers this" and recommend adding one.
- **Never claim tests pass or coverage is adequate.** That is the evidence file's
  job. Cite it.
- **Prefer the config fix.** When a rule would prevent the class, lead with that.
- **Report zero findings when there are none.** A padded review teaches the team
  to ignore reviews. State what you checked and that it was clean.
- **Rank by severity, and say what you did not check.** An honest gap is more
  useful than false completeness.
```

## Why the reviewer must not duplicate the gates

A reviewer that repeats gate conclusions produces two problems. It wastes the
review on things already proven, and it eventually **contradicts** a gate — at
which point the team has to decide which to believe, and the value of both drops
to zero.

The division is clean:

- **Gates** decide facts: does it compile, do tests pass, is the diff covered, do
  mutants survive, does the heap grow, are there CVEs.
- **The reviewer** handles judgement tools cannot reach: is this the right
  abstraction, does it match the spec, is the error handling coherent, is the
  boundary respected, is there a defect-catalog pattern present.

When the reviewer finds something that *should* be a fact, the correct output is
a recommendation for a new gate. That is how the harness improves: the review
surface shrinks over time as judgement calls get converted into gates.
